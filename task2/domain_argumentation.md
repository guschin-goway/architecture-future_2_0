# Task2 - Разделение на домены и моделирование потоков данных

## 1. Выделенные домены

### 1. Clinic Domain
Ответственность:
- Операционная деятельность клиник
- Приёмы, услуги, счета
- Управление персоналом и ресурсами

Не включает:
- Аналитическую логику
- Финансовые банковские продукты

---

### 2. Fintech Domain
Ответственность:
- Платежи
- Кредиты
- Банковские продукты
- Финансовая отчётность

Изолирован по регуляторным требованиям.

---

### 3. AI Domain
Ответственность:
- Анализ медицинских данных
- Работа со снимками
- ML-модели

Полностью изолирован от аналитической витрины.

Медицинские карты НЕ попадают в Data Platform.

---

### 4. Partner Integration Domain
Ответственность:
- Подключение фармацевтических компаний
- Подключение производителей электроники
- API-контракты

Позволяет подключать новых партнёров без изменения других доменов.

---

### 5. Data Platform Domain (Data Mesh)
Ответственность:
- Приём событий от доменов
- Формирование domain data products
- Предоставление аналитических данных
- Семантический слой

Не содержит операционной логики.

---

## 2. Почему именно такое разделение

### Принцип 1: Domain Ownership
Каждый домен:
- владеет своими данными
- публикует события
- не зависит от DWH

### Принцип 2: Разделение операционного и аналитического контура

Операционный контур:
- Clinic
- Fintech
- AI

Аналитический контур:
- Data Platform
- BI

Это устраняет необходимость внедрять бизнес-логику в DWH.

---

## 3. Потоки данных и поддержка бизнес-сценариев

### Сценарий 1: Быстрая отчётность
Clinic/Fintech -> EventBus -> Data Platform -> Semantic Layer -> BI

Результат:
- Нет тяжёлых batch-трансформаций
- Отчёты формируются за минуты

---

### Сценарий 2: Подключение нового финтех-сервиса

Новый сервис:
- Разворачивается внутри Fintech Domain
- Публикует события
- Data Platform автоматически принимает их

Не требуется:
- Изменять DWH
- Менять логику клиник

---

### Сценарий 3: Использование ИИ для анализа

Clinic -> AI Domain -> Результат обратно в Clinic

Аналитическая витрина:
- Получает только агрегированные события
- Не получает медицинские карты

Обеспечивается соответствие регуляторике.

---

### Сценарий 4: Подключение фармацевтической компании

Partner -> Partner API -> EventBus

Далее:
- Данные попадают в нужный домен
- Или формируется новый domain data product

Без изменения остальных доменов.

---

## 4. Преимущества для бизнеса

### 1. Ускорение вывода продуктов
Новый продукт = новый сервис + публикация событий.
Нет изменений в монолитном DWH.

---

### 2. Снижение зависимости от DWH
DWH перестаёт быть центром всей логики.
Он становится частью Data Platform.

---

### 3. Независимое масштабирование
Fintech может масштабироваться отдельно от клиник.
AI может использовать GPU-кластеры независимо.

---

### 4. Снижение регуляторных рисков
- Медицинские данные изолированы
- Финансовые данные изолированы
- В аналитике используются только разрешённые наборы

---

### 5. Готовность к экосистеме
Новые направления добавляются как новые домены.
Не требуется рефакторинг всей системы.

---

## 5. Итоговое состояние через год

- DWH больше не является центром архитектуры
- Домены развиваются независимо
- Data Platform получает данные через события
- Self-service BI работает поверх семантического слоя
- Партнёры подключаются через интеграционный домен
- Медицинские данные защищены и изолированы
